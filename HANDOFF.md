# pv1 — handoff context (office-pack build)

Vite + React + React Three Fiber (`@react-three/fiber` / `@react-three/drei` / `@react-three/postprocessing`) single-page 3D portfolio for Ronit Lad, a cybersecurity Master's student looking for a paid co-op in Canada. One scene: a 90s office cubicle, viewed through a scripted (non-orbit) camera, with a resume-style Win98-style UI rendered onto a monitor's screen.

**This is a from-scratch model swap of an earlier build** (same repo, edited in place — no fork). The original build used a single hand-authored `desk.glb`; this one uses a large third-party Sketchfab-style pack (`90s_retro_office_pack.glb`, ~56MB, ~141 top-level parts, no useful names on most of them) and everything downstream — camera, lighting, screen fit, edit-mode workflow — was rebuilt around it. If you see references to "the desk model" in old comments/history, that's the previous build, not this one.

Dev server: `npm run dev` from this folder, `http://localhost:5173` (or next free port). `.claude/launch.json` has a `pv1-dev` preview config already set up.

## The core recurring workflow — READ THIS FIRST

Almost every session on this project follows the same loop, and it's the single most important thing to understand before touching code:

1. User has edit mode open in their own browser (it defaults to **on** — see `editStore.js`), selects an object, drags/rotates/scales it with the gizmo.
2. User clicks **"Copy all as code"** in the edit-mode panel and pastes the resulting `{ id: { position, rotation?, scale? } }` block into chat — **with no other text**, or with a one-line instruction alongside it.
3. Your job: diff it against whatever's currently baked into the code, and bake **only the changed entries** into the matching constant (`PART_OFFSETS` in `OfficePack.jsx` for pack parts, `SCREEN_POSITION`/`SCREEN_ROTATION`/`SCREEN_SCALE` in `DeskPC.jsx` for the screen, `LAMP1_*`/`LAMP2_*` in `OfficePack.jsx` for the lights). Don't just leave pasted values as one-off overrides — they need to survive as the new baseline.
4. If a pasted block includes a `// removed - delete these...` array (see "Remove" feature below), add those ids to `REMOVED_PARTS` in `OfficePack.jsx`.
5. After every edit, check the dev server's console/HMR output for errors (`preview_logs` / `read_console_messages`) — you generally **cannot get a visual screenshot working** in the automated Browser pane for this project (see quirk below), so this console check is your only automated verification. The user verifies visually in their own browser and reports back with a screenshot or description.

Expect a rapid string of these paste-and-bake messages in any given session — that's normal, not a sign something's broken.

## Known environment quirk: automated Browser pane can't render this scene

The office pack has ~52MB of embedded textures (one alone is 13MB) across 160 images. In *this* automation environment, the Browser pane tab often reports `document.hidden: true` and refuses to composite frames for screenshots (`computer{action:"screenshot"}` times out with "the Browser pane is not displayed"). Combined with the large asset, the scene may never finish loading in that pane. Do **not** spend long stretches trying to force a screenshot — check `read_console_messages`/`preview_logs` for errors after every edit (fast, reliable, always works) and rely on the user's own browser for actual visual confirmation. If you need ground truth about DOM state, `javascript_tool` execution still works even when screenshots don't.

## Directory map (`src/`)

- **`scene/Experience.jsx`** — top-level scene: background colour, postprocessing (Bloom + Vignette), edit-mode/normal-mode camera switch, mounts everything else. No explicit lights of its own — visibility comes from `Environment`/`Lightformer` IBL plus the two lamp spotlights in `OfficePack.jsx`.
- **`scene/OfficePack.jsx`** — by far the most complex file. Loads `90s_retro_office_pack.glb`, and for every one of its ~141 top-level parts: bakes the part's full WORLD transform (position+rotation+scale, including the pack's own Z-up→Y-up axis-correction ancestors) into the part's own local transform, detaches it, and wraps it in its own `<Editable>` so it's individually selectable/draggable in edit mode. See in-file comments for exactly why (mesh geometry is baked directly into vertex data with node-level transforms at identity, so naive per-object rotation swings things wildly off-center — this bit us twice, once for the clock hands and once for the fan blade, before landing on a pivot-correction technique). Also owns:
  - `REMOVED_PARTS` (`Set` of part names) — parts flagged "Remove" in edit mode, filtered out of rendering entirely (not just hidden).
  - `PART_OFFSETS` (`{ [name]: { position?, rotation?, scale? } }`) — per-part nudges from edit mode, applied on top of each part's own baked (already-correct) transform.
  - A real-time analog clock (`Node_56_186`/`Node_57_188`/`Minute_Arm002_14` — auto-generated names, identified by inspection, not text). Hour/minute hand rotation axis was derived via PCA over actual mesh vertices (axis-aligned-bbox guessing was wrong and caused wobble), the pivot via a separate marker node (`Node_58_190`), and the real-time calibration (`CLOCK_TIME_OFFSET_MS`) via empirical testing against the user's actual clock (currently `-3h` exactly).
  - An oscillating fan blade (`Node_71_227`, unrelated to the differently-named `Fan_Blades_232` etc. which are a separate, already-removed fan) — same PCA-derived axis + pivot-correction technique, pivoted on its own centroid (an earlier attempt pivoted on `Node_73_231`, a completely different object — the stand — which "worked" in the sense of not flying off-screen but wasn't truly spinning in place).
  - Two `EditableSpotLight`s (`lampLight1`/`lampLight2`) — real spotlights (cone-shaped "V" of light, not omnidirectional), each wrapped in its own `<Editable>` with a nested `object3D` target so rotating the Editable tilts the cone. `lamp1` is anchored to `Node_25_117` (a lamp fixture in the pack); `lamp2` has no particular anchor. Both show a small white sphere marker in edit mode only (spotlights have no visible geometry of their own, making them hard to position blind).
  - Fan spin and both lamps' intensity are gated by `fanOn`/`lightsOn` props (default `true`), driven by `sceneControlsStore.js`.
- **`scene/CameraRig.jsx`** — the whole camera behavior, three fixed shots (`WIDE`/`TABLE`/`SCREEN_SHOT`), lerped every frame, no free orbiting in normal mode. All three shots are centered on `Monitor_002001_93`'s actual world position (computed from the glb, not eyeballed) — **not** the pack's origin, since the pack spans ~22m. The shots approach from world **+X** (this pack's screen's actual front normal, derived from `SCREEN_ROTATION` — a different direction than the old desk-scene build, which approached from +Z; reusing the old offsets caused a real "wrong side" bug, camera clipped into the wall). `SCREEN_RIGHT = (0,0,-1)` is the screen's actual "right" direction in world space, used for both `TABLE`'s parallax and `SCREEN_SHOT`'s edge-pan (hovering near an edge while zoomed pans the camera that way, proportional the whole time, strongest at the edges). Also exports `FrozenCamera`, a simple park-at-`WIDE` component swapped in via the `CAMERA_RIG_ENABLED` constant in `Experience.jsx` if the scripted dolly ever needs disabling again with zero other changes.
- **`scene/ScreenBridge.jsx`** — the OS, projected onto the CRT glass via drei's `<Html transform>`. The OS itself renders into an 800×600 wrapper (matching `os/os.css`'s `.win98-screen`) which is then CSS-`scale`d by `EMBED_SCALE` (from `os/embedScale.js`, currently 2) inside a doubled outer `<Html>` box — gives the browser more source pixels to downsample from (sharper text/icons) without touching any `os/*.jsx` layout code. `SCREEN_SCALE` in `DeskPC.jsx` is divided by that same factor to keep the on-screen size/position on the glass unchanged. `Window.jsx` also imports `EMBED_SCALE` (see the react-rnd bug below). No occlusion on the `<Html>` — `occlude="blending"` conflicts with the Bloom/Vignette `EffectComposer` and blanks the screen; plain raycast `occlude` was also tried and reverted (only tests one anchor point, so it either false-occludes when close to the monitor casing or looks like it's floating when backed off — no offset satisfies both). Relies entirely on `CameraRig`'s fixed shots keeping the camera at reasonable angles; free `OrbitControls` (edit mode only) is the one place a bad grazing angle is actually reachable.
- **`scene/DeskPC.jsx`** — despite the name, this is now just where `SCREEN_POSITION`/`SCREEN_ROTATION`/`SCREEN_SCALE`/`SCREEN_TARGET` live (currently `[5.41, 1.121, 4.106]` / `[-2.865, 1.565, 2.866]` / `[0.009, 0.008, 0.006]`). Also still exports the old `DeskPC` component + `Prop`-based loader for the original `desk.glb`, but **nothing renders it anymore** — kept on disk unreferenced rather than deleted, per an explicit "keep the structure as-is, don't delete" instruction from early in the office-pack pivot. Same for `FloorLamp.jsx` and the `desk`-model path through `Prop.jsx`.
- **`scene/Editable.jsx` + `editStore.js` + `EditModeOverlay.jsx`** — the layout editor. `editStore.js` defaults to **`enabled: true`** now (it used to default off) — reasoning: with the scripted camera off during heavy pack-layout work, free `OrbitControls` was needed by default; it's stayed on since. The overlay panel got a **"Remove" feature** this session: a button next to "Reset this object" that flags an id in `state.removed` — doesn't touch the live scene at all, just excludes that id from the position listing in "Copy all as code" and instead appends it to a separate `// removed - delete these...` array. `Editable` itself now also accepts/forwards a `scale` prop (added when the first part needing a scale offset came up — wasn't wired through originally).
- **`scene/IntroHUD.jsx`** — typewriter name/title/tagline + live clock, top-left, starts on first click (via `CameraRig`'s `onStart`). Now also renders two small round "F"/"L" toggle buttons below the clock (only once typing is done) — fan and lights on/off, reading/writing `sceneControlsStore.js`. Buttons need `pointerEvents: 'auto'` set explicitly since the parent `.intro-hud` is `pointer-events: none`.
- **`scene/sceneControlsStore.js`** — tiny external store (`useSyncExternalStore`, same pattern as `editStore.js`) holding `{ fanOn, lightsOn }`, both default `true`. Bridges `IntroHUD` (outside `<Canvas>`) and `OfficePack.jsx` (inside it).
- **`os/`** — the resume UI: boot screen, desktop icons, taskbar/start menu, draggable windows (`react-rnd`). Fixed 800×600 `.win98-screen` (see `os.css`), independent of the 3D scene and the `EMBED_SCALE` doubling above (`embedScale.js` is the one exception — a tiny shared constant both sides import, so the OS layer doesn't reach into `scene/`).
  - **`windows/registry.jsx`** — `WINDOWS` map (`id -> { title, icon, Component, size, pos }`) plus `DESKTOP_ICONS`. Has a `centered({width, height})` helper (accounts for the 30px `.taskbar` pinned to the bottom — true usable height is 570, not 600) used by `showcase`'s `pos` (a getter, computed from its own `size`) instead of a hand-guessed pixel offset. If another window needs centering, reuse `centered()`, don't hand-derive numbers again.
  - **`windows/ShowcaseWindow.jsx`** — stripped down this session to just name + a short role label ("Cybersecurity Analyst" — a display-only string local to this component, **not** pulled from `profile.tagline`/`role` in `data/content.js`, which stay as their fuller original wording since they're used elsewhere) + four plain `<a>` nav links (not buttons) to about/skills/projects/contact, styled as classic underlined blue hyperlinks in `os.css`. Modeled visually on henryheffernan.com's showcase window (centered content, text links).
- **`index.css`** — global page CSS. **No more `.vintage-vignette`** (see below) — just `.intro-hud` typewriter styling.
- Reused unchanged: `main.jsx`, `App.jsx`, `hooks/useMediaQuery.js`, `data/content.js`, `mobile/*`.

## Things added, then fully removed this session (don't be surprised if you see references in old context)

- **Night mode**: a toggle button + animated vignette + lamp on/off, all built out then explicitly ripped out at the user's request ("ditch the night mode completely"). `nightModeStore.js` and `NightModeButton.jsx` were deleted outright.
- **`.vintage-vignette`** (the flat, screen-space DOM overlay that used to darken the corners): removed entirely at the user's request ("stay in environment, not fixed to my screen") — it didn't react to camera movement or the 3D scene at all, unlike the real WebGL `<Vignette>` from `@react-three/postprocessing` (already in `Experience.jsx`'s `EffectComposer`), which is recomputed with the actual render every frame. That WebGL vignette's `darkness`/`offset` were pushed up (0.85→0.95, 0.25→0.35) to compensate for the removed layer.
- **Lamp glow DOM overlay** (`LampGlowProjector`, `.lamp-glow`): built to make the lamps' glow bypass the (now-removed) night-mode vignette via a `mix-blend-mode: screen` layer projected from 3D to 2D each frame. Removed along with night mode since the thing it was working around no longer exists.

## Open / worth knowing before the next session

- **"It stays at bottom right" — actually solved now, take 2.** The `EMBED_SCALE`/`scale={EMBED_SCALE}` fix described below was real but incomplete: it assumed passing the right `scale` number to react-rnd would make its internal mount-time correction land correctly. It doesn't, and can't - `Rnd.componentDidMount` calls `updateOffsetFromParent()` (measures `getBoundingClientRect()` against the `scale` prop) and then actively repositions via `this.draggable.setState(...)`, assuming the only ancestor transform is a **uniform 2D `scale()`**. Our real ancestor is drei's `<Html transform>` - a full 3D `matrix3d` built from the screen mesh's position/rotation/scale, reprojected by the camera every frame, whose effective on-screen magnification changes with whichever shot (`WIDE`/`TABLE`/`SCREEN_SHOT`) the camera happens to be on at the moment the window mounts. No constant `scale` value can make that correction come out right - confirmed by reading react-rnd's own source (`node_modules/react-rnd/lib/index.js`) rather than guessing further. Verified live: with only the `EMBED_SCALE` fix, a fresh page load still opened the showcase window clearly shifted toward the bottom-right of the desktop.
  - **Actual fix, in `Window.jsx`:** stopped trying to make the measurement-based correction accurate, and instead let it run, then immediately snap the position back to the real intended default (`win.pos`) via react-rnd's own imperative `updatePosition({x,y})` method (accessed through a `ref` on `<Rnd>`), inside a `useLayoutEffect` (fires before paint, so there's no visible flash of the wrong position). `scale={EMBED_SCALE}` is kept on `<Rnd>` for its other job (converting real pointer-drag deltas into logical desktop pixels while actively dragging/resizing) - still an approximation for the same underlying reason, but out of scope for the centering bug specifically.
  - Verified live end-to-end on a genuinely fresh page load (not just HMR): boot → desktop → showcase window opens with even margins on all sides above the taskbar.
- If `EMBED_SCALE` in `embedScale.js` ever changes, three things need to move together: the CSS `scale()` and outer `<Html>` box size in `ScreenBridge.jsx` (both already read the constant), `SCREEN_SCALE` in `DeskPC.jsx` (divide by the new factor, currently `[0.009, 0.008, 0.006]` for `EMBED_SCALE=2`), and `Window.jsx`'s `scale={EMBED_SCALE}` prop (already reads the constant, no action needed there beyond the import staying correct).
- The screen's rotation (`SCREEN_ROTATION`) is quite extreme (`[-2.865, 1.565, 2.866]` rad) — this was arrived at through several rounds of live dragging, not derived, so don't assume it's "wrong" just because the numbers look unusual.
- `LAMP_INTENSITY = 25` is a tuned-by-request value with headroom to go further if asked (comment explains why it's so much higher than a "realistic" light).
- Fan spin direction/speed (`FAN_SPIN_SPEED = 10` rad/sec) and clock hand spin direction were both determined empirically via user screenshots this session — if either the fan or the clock ever need their axis/pivot/sign touched again, re-derive via PCA over actual vertex data (see the node-script technique referenced in `OfficePack.jsx`'s comments) rather than guessing from a bounding box, which has been wrong twice already.
